# Falcon Time Tracker — Веб-приложение для учёта рабочего времени сотрудников

Тестовое задание для **Falcon AI**. Небольшое самодостаточное веб-приложение для учёта рабочего времени сотрудников компании, созданное с использованием ИИ-агентов, с атомарным сохранением данных на диск и покрытием ключевых сценариев автотестами.

---

## 1. Что реализовано

* **Добавление сотрудников** (`POST /api/employees`, `GET /api/employees`) — ФИО и должность (по умолчанию предзагружены 3 вымышленных сотрудника для быстрой проверки).
* **Запуск и остановка таймера с описанием задачи** (`POST /api/timers/start`, `POST /api/timers/stop`) — контроль активной сессии сотрудника, защита от повторного параллельного запуска (`409 Conflict / TIMER_ALREADY_RUNNING`) и корректный запуск нового таймера после остановки предыдущего.
* **Просмотр записей и общего времени каждого сотрудника за выбранный период** (`GET /api/reports?from=YYYY-MM-DD&to=YYYY-MM-DD&employeeId=...`) — сводная таблица по каждому сотруднику + детальный журнал задач + корректная обработка пустого отчёта (`isEmpty: true`).
* **Сохранение данных после перезапуска приложения** — все изменения атомарно записываются в `data/store.json` через временный файл (`.tmp` + `fs.renameSync`), поэтому перезапуск сервера не теряет ни сотрудников, ни активные/завершённые таймеры.

---

## 2. Быстрый запуск и проверка

Требуется только **Node.js >= 18** (внешние npm-зависимости не требуются, используются нативные модули `node:http`, `node:fs`, `node:test`).

```bash
# 1. Запуск автотестов (проверка пустого отчёта, повторного запуска таймера, фильтра периода и перезапуска)
npm test

# 2. Запуск веб-приложения
npm start
# Откройте в браузере: http://localhost:3000
```

## 4. Примеры запросов (промптов) к ИИ

### Промпт 1 — Генерация ядра хранения и бизнес-логики таймеров
> «Напиши на Node.js (CommonJS, без внешних зависимостей) класс `TimeTrackerStore`, который хранит список сотрудников и записи рабочего времени в JSON-файле на диске. Нужны методы: `addEmployee({ name, role })`, `startTimer({ employeeId, task, now })`, `stopTimer({ employeeId, entryId, now })`, `getReport({ from, to, employeeId, now })`. Обязательно запрети запуск второго активного таймера для одного и того же сотрудника (выбрасывай ошибку со `statusCode = 409` и `code = 'TIMER_ALREADY_RUNNING'`), поддержи передачу параметра `now` для детерминированных unit-тестов и возвращай структуру `summaryByEmployee` с общим временем каждого сотрудника за период».

### Промпт 2 — Генерация веб-интерфейса
> «Создай адаптивный `public/index.html` на чистом HTML/CSS/JS для работы с эндпоинтами `/api/employees`, `/api/timers/start`, `/api/timers/stop` и `/api/reports`. Выведи форму добавления сотрудника, форму запуска таймера с описанием задачи, таблицу текущих сотрудников с кнопкой "Остановить" для активных таймеров и блок отчёта с фильтром по датам (`from`, `to`) и сотруднику. Если за период записей нет (`report.isEmpty === true`), отображай понятный блок пустого отчёта».

### Промпт 3 — Генерация тестов граничных сценариев
> «Напиши тесты на встроенном `node:test` и `node:assert/strict` для `TimeTrackerStore` с использованием временной директории `os.tmpdir()`. Покрой 5 обязательных сценариев: 1) пустой отчёт; 2) добавление сотрудника и валидация пустого имени; 3) повторный запуск таймера (ошибка 409 при уже идущем таймере и успешный повторный запуск после остановки); 4) расчёт общего времени по каждому сотруднику за выбранный диапазон дат; 5) сохранение данных после перезапуска (создание второго инстанса `TimeTrackerStore` поверх того же файла)».

## 5. Какие ошибки в сгенерированном ИИ коде были найдены и исправлены

1. **Ошибка фильтрации правой границы периода (`to = YYYY-MM-DD`):**
   * *Что сгенерировал ИИ:* В первой версии ИИ парсил `new Date(to)`, что для строки `'2026-10-27'` создавало `2026-10-27T00:00:00.000Z` (начало суток). Из-за этого все записи за сам день `2026-10-27` (например, в `18:00`) отбрасывались фильтром `startMs > toMs`.
   * *Как исправлено:* В `src/store.js` добавлена явная нормализация даты формата `YYYY-MM-DD`: для `from` выставляется `T00:00:00.000Z`, а для `to` — конец суток `T23:59:59.999Z`. Добавлен тест на запись в `18:00` последнего дня периода.
2. **Дублирование активных таймеров при повторном нажатии «Запустить»:**
   * *Что сгенерировал ИИ:* Первоначальный вариант просто пушил новую запись с `endTime: null` в массив `entries`, позволяя одному сотруднику запустить несколько таймеров одновременно, что искажало суммарное время.
   * *Как исправлено:* В `startTimer()` добавлена проверка `this.state.entries.find(e => e.employeeId === employeeId && e.endTime === null)`. Если активная запись уже есть, возвращается `409 Conflict` (`TIMER_ALREADY_RUNNING`), а новый таймер разрешается запускать только после остановки текущего.
3. **Обнуление коротких интервалов (`0 сек`) при быстрой остановке таймера в UI:**
   * *Что сгенерировал ИИ:* Использование `Math.floor((endMs - startMs) / 1000)` приводило к тому, что при остановке таймера быстрее чем через 1 секунду длительность сохранялась как `0`, и запись выглядела «пустой».
   * *Как исправлено:* В `stopTimer()` добавлено округление с нижней границей `Math.max(1, Math.round((endMs - startMs) / 1000))`.
4. **Риск повреждения JSON-файла при перезапуске (`fs.writeFileSync` напрямую в `store.json`):**
   * *Что сгенерировал ИИ:* Прямая перезапись `fs.writeFileSync(this.filePath, ...)` может оставить пустой или обрезанный файл при аварийной остановке процесса.
   * *Как исправлено:* В методе `_save()` реализована атомарная запись сначала во временный файл `${this.filePath}.${process.pid}.${Date.now()}.tmp`, а затем атомарный `fs.renameSync(tmpPath, this.filePath)`.
